# Process gaps found in orakl, and what Skullery does instead

Read-only survey of the orakl repo on 2026-10-28. Each line: the cause, what it costs, and the rule or tool the Skullery repos (larder and skullery) use instead. The npm login item comes first because the owner named it.

| # | Gap in orakl | Cause | Cost | Skullery instead |
|---|---|---|---|---|
| 1 | Log in to npmjs or approve a package on a website | The publish workflow stages two workspace packages with `npm stage publish` under npm trusted publishing (OIDC). npm holds every staged version until a maintainer approves it with 2FA, on npmjs.com or with `npm stage approve`. The trusted-publisher binding itself is set by hand in each package's settings on npmjs.com. The process doc repeats the approval as a required step before the client sync. | A human web step on every protocol or shared bump, blocking the release of the client. A dashboard setting that lives outside the repo. | Nothing is published to a registry. `larder_api` is consumed from the skullery git repo pinned to a commit, the private core from a path or a git dependency pinned to a commit. If a package ever goes to pub.dev, `dart pub publish` has no staging approval, only a one-time pub.dev account; it is not planned. Versions are exact in pubspec.yaml, pubspec.lock is committed, `dart pub outdated` runs in CI, Dependabot (`package-ecosystem: pub`) opens the bump pull requests. No step asks a human to click. |
| 2 | Version updates are off | dependabot.yml sets `open-pull-requests-limit: 0`; no Renovate. | Drift is found by hand with `pnpm outdated`, or not at all. | Dependabot for pub, weekly, limit 5, grouped minor and patch. `dart pub outdated` as a CI step that reports, and a monthly bump commit with the three dependency facts. |
| 3 | Build-script approval at install | pnpm asks `pnpm approve-builds` for packages with install scripts; `allowBuilds` in pnpm-workspace.yaml and `onlyBuiltDependencies` in package.json disagree. | A terminal prompt on a fresh install and two sources of truth. | pub has no install scripts, nothing to approve. A Dart build hook (`hook/build.dart`) is visible code in the package and runs without a prompt. |
| 4 | CI runs only by hand | ci.yml has `workflow_dispatch` only; no push or pull request trigger. The gate is the local `typecheck && lint && test`. | Nothing enforces the gate. A red main is possible. | A CI workflow on push and pull request from day one of CI: `dart analyze`, `dart format --set-exit-if-changed`, `dart test`, the leak check, and in skullery the clean-clone stub build. Required status checks once branch protection starts at the first deploy. |
| 5 | No secret scanner | No gitleaks or equivalent in hooks, scripts or CI. The agent settings only deny reads of env files. A plaintext service token sits in .mcp.json. | A leaked token is found by luck. Rotate that token. | `tool/leak_check.sh` in both repos: runs on every `git commit` through a Claude Code hook, in CI, and on demand. Same-day rotation rule in CLAUDE.md. |
| 6 | Env handling | 21 variables in .env.example, read with `process.env` in several files, no validation, missing values fail at runtime. | A wrong local setup fails late and in odd places. | No env file in any repo, not even an example. Local work needs no secret: the core runs on a SQLite file. At the first deploy, one typed config class reads the host's variables at startup and fails fast with the variable name. |
| 7 | Credentials kept in three places | The same test logins must exist in GitHub secrets, the Fly review app and the Claude Code environment. | Manual sync, drift, and secrets inside AI sessions. | One place: the host's secret store, fed from GitHub Actions secrets by CI. Claude sessions never hold a secret. No test accounts until cooks exist, and then invented ones seeded by CI. |
| 8 | Machine setup needs logins and a hand-filled env | setup script expects `gh auth login`, `fly auth login` and a copied .env. | A new machine or agent cannot build without a human. | Setup is Dart from Homebrew plus `gh auth login` for pushes. `dart pub get && dart test` works with nothing else. skullery builds on a clean clone with the stub. |
| 9 | Public code is a mirror | The client is developed in the private repo and synced to a public repo by a script that opens a pull request; merging it deploys production. | Generated history, a release hidden in a merge, two repos to keep in step. | skullery is a first-class public repo with its own history. larder is a dependency it never sees. Each repo deploys from its own main through pull requests. |
| 10 | CLAUDE.md is a loader | CLAUDE.md holds only `@AGENTS.md`; AGENTS.md mixes working style, commands and repo facts, and parts of it are copied verbatim into the client repo. | Duplication and drift between two copies. | CLAUDE.md holds the rules, CONTEXT.md holds what the system is, README.md holds the stranger's view. Each repo has its own three files, nothing copied. |
| 11 | 46 skills and 8 agents, several unused | Skills bound to Svelte, Playwright, shadcn, tend config and meridian maps; agents auditor, drill and sweeper have no trace in the git log. | Context spent on loading, maintenance of unused files. | Five agents (scout, verifier, refuter, reviewer, builder) and seven skills, each with a purpose line. A new one needs a use in a session first. |
| 12 | Push to main blocked from day one | A hook blocks every push to main, before anything deploys. | Branch and pull request ceremony with no reader. | Rule 16: push to main until the first deploy. The no-push-main hook and branch protection arrive with the first deploy. |
| 13 | Conventional commits checked on `-m` only | The hook parses the first `-m` of a `git commit`; squash-merge titles bypass it, four of the last forty subjects do not conform. | The log is mostly, not fully, conventional. | Same hook now; a commit-message check on pull request titles in CI once pull requests start. One commit per logical part. |
| 14 | Review needs orchestrators | The adversarial review runs inside convoy, transit and crucible with repo-specific config, rosters and run folders. | Heavy to start, hard to run for a single commit. | The review skill: reviewer on a commit range, refuter on each CONFIRMED finding, fix what survives, gate, push. No orchestrator, no config. |
| 15 | Manual dashboard steps are undocumented | The storage bucket is created by hand in the Cloudflare dashboard; the database provider's data processing agreement needs a plan upgrade; webhook secrets are copied from a sandbox dashboard. | Steps live in heads, not in the repo. | Every one-time dashboard step is written into CONTEXT.md the day it is done, with the setting name and the date. Images are served through the Worker, so no bucket is public. The data agreement is checked before cook accounts exist. |
| 16 | Hooks that need Node | Session logging, graph index and failure hints run as Node scripts on every tool call. | A Dart repo would need Node just for the hooks. | Two bash hooks that need bash and jq only: conventional commit subject, leak check. |
| 17 | Documentation drift checked by habit | A rule says docs state the system as it is; no check runs. | Stale docs survive. | The parse-check skill keeps the counts in CONTEXT.md in step; the review skill checks CONTEXT.md as the yardstick; a doc that names a count or a path is checked by the verifier agent before a push. |
